## 0. 为什么现在能做

三件事同时成立,这件事的启动成本比看起来低得多。

### 0.1 资产侧:203 个表情 morph 已经躺在 PMX 里

`pmx2glb.mjs` 的文件头写着「不支持:变形器 morphs(表情)、物理、IK、toon/sphere 贴图」。所以这批资产从没进过 GLB。实测 PMX 源:

| 模型 | morph 总数 | 类型分布 | 影响元素合计 | 命名体系 |
| --- | --- | --- | --- | --- |
| `si`(终末地·祀) | 41 | 40 vertex + **1 material** | 50,932 | MMD 传统日语名 + 少量符号(`▲` `∧` `ω`) |
| `akane`(异环·明音凛) | 162 | 162 vertex | 153,138 | **四套体系混合**,见下 |
| `yelan`(原神·夜兰) | 未测 | — | — | PMX 源不在库内,只有 GLB |

`akane` 这一个模型自带的东西,值得单独列出来:

- **`EL_<情绪>_OP` / `EL_<情绪>_CLO` 成对结构** —— `EL_Happy_l_CLO`、`EL_Surprised_01`、`EL_Angry_01_OP`、`EL_Sad_01_CLO`、`EL_Despise`、`EL_Doubt`、`EL_Evil`、`EL_Tired`、`EL_Serious`、`EL_Thinking`。`OP`/`CLO` = 睁眼版 / 闭眼版。**这正是「笑着眨眼时眼皮穿过脸」这个经典问题的厂商原生解法** —— 情绪表情自带闭眼变体,眨眼时切到 `_CLO` 而不是叠加眼皮。
- **`look_U / UR / R / RD / D / DL / L / LU`** —— 8 方向视线 morph。
- **`jawOpen` + `jawOpen_a/yi/wu/ei/o`** —— 口型五元音,另有 `jawOpen_<情绪>_OP/CLO` 的组合态。
- **`mouthPucker / mouthFunnel / mouthRollUpper / mouthRollLower`** —— ARKit 风格的命名。
- **`TD_*` / `TDS_*`(漫画符号层)** —— `TD_Veins`(井字怒符)、`TD_Sweaty`、`TDS_liulei`(流泪)、`TDS_leizhu`(泪珠)、`TDS_StarEyes`、`TDS_yunxuan`(晕眩)、`TDS_heixian`(黑线)、`TDS_lianhong`(脸红)、`TDS_shengluehao`(省略号)、`TDS_Flower`……一整套二次元情绪符号。
- **`EB_*`(眉毛)** —— `EB_UD_L/R`、`EB_Rotate_01/02`、`EB_Thinking_01`。
- **`biyan` / `biyan1` / `biyan_L/R`** —— 眯眼。

**没有任何一个 morph 是空壳**(`elementCount` 全 > 0)。这不是「模型自带一点点表情」,这是**一套完整的、厂家做过资源管理的表情系统**,只是被转换管线整个丢掉了。

### 0.1.1 两个模型的能力差距(实测)

用 `pipeline/morph-survey.mjs` 对 §3.2 的 35 个槽位做覆盖率体检,结果差异极大:

| | `si`(终末地·祀) | `akane`(异环·明音凛) |
| --- | --- | --- |
| morph 总数 | 41 | 162 |
| 影响元素合计 | 50,932 | 153,138 |
| 空壳 morph | 0 | 0 |
| **槽位覆盖** | **22 / 35** | **35 / 35** |
| 视线 8 方向 | ❌ 全缺(无 `look_*`) | ✅ 全有 |
| 漫画符号 | ❌ 只有「照れ」 | ✅ 全 6 个(汗/泪/怒符/星星眼/黑线/脸红) |
| 未被认领的 morph | 15 个(`▲` `∧` `ω` `にやり` `ぺろっ` …) | 70 个(`jawOpen_*` 组合态、`EL_*_OP` 睁眼版、`mouthPucker/Funnel` …) |

**这张表是设计里「必须支持能力探测 + 优雅降级」的直接依据。** 同一个游戏里,`akane` 能做脸红和 8 方向视线,`si` 做不了。指令协议不能假设所有角色能力相同 —— 所以 §3.3 的 manifest 必须有 `unresolved` 字段,消费方必须能查询「这个角色会不会脸红」。

## 1. 边界:谁负责什么

这条线必须在动手前画清,否则「表情层」会长成一个塞满 LLM 调用的怪物,违反 `AGENTS.md` 的「引擎只管怎么渲,不写游戏概念」。

```
┌─────────────────────────────────────────────────────────┐
│  消费方（witch-idle / 未来的 AI 桥 / 行为树）              │
│                                                          │
│   · 解析 LLM 输出里的 [happy] 标记                        │
│   · 决定「什么时候开心」——情绪状态机、亲和度、时间        │
│   · 口型文本对齐（TTS 时间戳 → viseme 序列）              │
│   · 把上面的结果翻译成指令                                │
└───────────────────────────┬─────────────────────────────┘
                            │  witch.exp/1 指令（§6）
┌───────────────────────────▼─────────────────────────────┐
│  nijimi 引擎（角色层）                                    │
│                                                          │
│   · ExpressionLayer：槽位 → 权重 → morph / 材质 / 眼骨    │
│   · 自动层：眨眼节律、视线游移、情绪衰减曲线               │
│   · 与 Rig / PosePlayer / CharacterAnim 的通道仲裁         │
│   · 契约：expression-manifest.json（读，不猜）             │
└─────────────────────────────────────────────────────────┘
```

**【判断】引擎不认识「开心」的语义。** 引擎只认识槽位名 `happy` 和它的权重。谁来决定 `happy` 该是 0.6 还是 1.0、该持续多久、要不要配一个挥手动作 —— 那是消费方的事。

**【判断】引擎不解析 LLM 文本,也不做文本清洗。** 参考项目 `Open-LLM-VTuber` 在引擎侧做 `remove_emotion_keywords()`(正则剥掉 `[joy]`,否则 TTS 会把「bracket joy bracket」念出来)【外部】—— 这个活儿属于消费方的 LLM 桥,不属于渲染引擎。

## 2. 参考项目:同类是怎么做的

我实地读了六个开源项目的文档与源码说明。按与本项目的相关度排:

### 2.1 对照表

| 项目 | 形象方案 | 值得抄的机制 |
| --- | --- | --- |
| **Open-LLM-VTuber** | Live2D | `emotionMap` 配置表(语义键 → expression 索引或名字);LLM 输出内嵌 `[joy]` 标记;`extract_emotion()` 提取;`tapMotions` 点击区域 → 动作名 + 权重随机触发 |
| **waifu-rt3d** | VRM + three-vrm | **6 层动画管线**(下详);5 个 personality 浮点参数缩放全部动画参数;emotion tag → blend shape,**300 ms lerp**;FFT 频谱 → 3 个 viseme(aa/ou/ee) |
| **ChatVRM_vue / Amica** | VRM | `ExpressionController` + `AutoBlink` + `AutoLookAt` 三层;**AutoBlink 只在 neutral 时启用**,出现任何情绪就关闭;**口型权重随情绪降级**(neutral 时 50%,有情绪时 25%) |
| **cyber-waifu-desktop-pet** | 立绘/SVG、Live2D、glb/VRM 可切换 | **渲染器可切换架构**(同一套指令喂不同形象);多动作**合并成单个多动画 GLB**,用 `animationName` 切换(无重载无闪烁) |
| **Lia**(Godot) | VRM | 四层切分:Stage(窗口/OS)/ Body(渲染 + 智能 hitbox)/ Brain(HTTP → 本地 AI + 情绪解析)/ Behavior(FSM:Idle/Roaming/Hiding) |
| **Agent-desktop-pet** | Live2D | **9 个 Agent 状态 → 9 个表情**的纯状态映射;眼睛跟鼠标带惯性 + 回正动画 |
| **VRM 1.0 规范** | VRM | Expression 可组合三类 binding(下详);**Override 系统** `overrideMouth/overrideBlink/overrideLookAt`,策略 `none`/`block`/`blend` |

### 2.2 抄什么

**【判断】抄这五条:**

1. **情绪标签协议,但放在消费方。** `[joy]` 这种内嵌标记对 LLM 极其友好(它就是在写自然语言),prompt 里注入可用标签列表即可。但标记的解析归消费方 —— 我们的引擎收到的是结构化的 `face.play('happy')`。
2. **Override 仲裁,而不是开关。** `ChatVRM` 的「有情绪就关掉自动眨眼」是粗粒度开关。VRM 1.0 的 `overrideBlink: 'blend'` 是连续量 —— 笑着眨眼时,眼皮权重随笑容强度衰减,而不是硬关。**我们抄 `blend`。**
3. **口型权重随情绪降级。** 说话时的嘴型不该把「笑」抹平。参考值:无情绪时口型权重 50%,有情绪时 25%【外部】。
4. **`OP`/`CLO` 成对表情的用法。** `akane` 自带闭眼变体,这比叠加法优雅:情绪最高权重时若在眨眼,整体切到 `_CLO` 态,而不是让两组顶点位移打架。
5. **多动作合并成单个 GLB + `animationName` 切换。** 本项目 `anims/<名>.anim.glb` 已经是「动画-only GLB」的路子,再往前一步就是「一个 `motions.glb` 装所有动作」。

**【判断】不抄这两条:**

- **不抄 6 层完整管线。** `waifu-rt3d` 的 22 种待机小动作、14 个触发动作、FFT 口型,对「桌面伴侣」是对的,对 diorama 放置游戏是过度的。我们抄的是**分层的思想**,不是层的数量(§7 裁剪到 3 层新增)。
- **不抄 Live2D 参数模型。** Live2D 是 2D 参数变形(嘴张开度 30%、眼睛缩放 110%),我们的模型是 3D 顶点 morph。Live2D 的「参数」概念在我们的世界里对应的是**多个 morph 的加权组合**,不是单一标量。

## 3. 数据模型:语义槽位 → 通道 → 绑定

这是整个设计的骨架。核心动机:**模型作者怎么命名 morph,与游戏怎么说话,必须是两件事。**

### 3.1 三层

```
语义槽位（引擎与游戏之间的语言，稳定、跨模型）
   happy / sad / angry / surprised / relaxed / shy
   blink_l / blink_r / blink           ← 眨眼
   mouth_a / mouth_i / mouth_u / mouth_e / mouth_o
   look_u / look_ur / look_r / ...      ← 8 方向
   brow_up / brow_down / brow_angry
   symbol_sweat / symbol_tears / symbol_angry_vein ...   ← 漫画符号
        │
        │  由 expression-manifest.json 声明（转换期产出，运行期只读）
        ▼
通道（channel：一个可被写入的具体属性）
   · morph:  meshIndex / targetIndex
   · material: materialIndex + 属性（diffuse / alpha / 颜色）
   · bone:   骨骼名 + 轴
        │
        ▼
绑定（binding：一个槽位可以绑多个通道，权重合成）
   happy = 0.7 × morph[笑い] + 0.3 × morph[なごみ]
   照れ  = 1.0 × material[材质 11].diffuse.lerp(红)
```

**【外部】这不是我发明的形状。** VRM 1.0 的 Expression 正是「一个表达式 = 一组 binding」:`MorphTargetBind`(顶点)、`MaterialColorBind`(材质颜色,用于脸红/瞳色)、`TextureTransformBind`(UV 偏移,用于眼纹理滚动),一个 expression 可以同时含多种 binding【外部,getanimate PMX→VRM 指南】。

### 3.2 槽位清单（**已定稿 2026-10-17**）

**【判断】分七组，共 35 个。** 组内是「可独立寻址的最小单位」，组间是语义关系。
定稿后这 35 个名字就是对外协议，写在 `pipeline/expression-rules.mjs` 的 `SLOTS`（唯一源），
本表为它的镜像 —— 改名必须两处一起改。

| 组 | 槽位 | 说明 |
| --- | --- | --- |
| **情绪**(6) | `happy` `sad` `angry` `surprised` `relaxed` `shy` | 高层的「表情包」。每个情绪实际是一组 binding 的合成 |
| **眨眼**(3) | `blink` `blink_l` `blink_r` | 双眼 / 左 / 右 |
| **眼型**(4) | `squint`(眯) `eye_wide`(瞪) `pupil_small`(瞳小) `highlight_off`(高光灭) | 动画演出用,比情绪更底层 |
| **口型**(5) | `mouth_a` `mouth_i` `mouth_u` `mouth_e` `mouth_o` | 对齐 MMD あいうえお / VRM aa·ih·ou·ee·oh |
| **视线**(8) | `look_u` `look_ur` `look_r` `look_rd` `look_d` `look_dl` `look_l` `look_lu` | 只在 `gazeMode: 'morph'` 的模型上有 |
| **眉**(3) | `brow_up` `brow_down` `brow_angry` | |
| **符号**(6) | `symbol_sweat` `symbol_tears` `symbol_vein` `symbol_star_eyes` `symbol_black_line` `symbol_blush` | 漫画符号,diorama 里是「演出道具」 |

情绪槽位的**实现是合成**:`happy` 在一个模型上可能是 `笑い`,在另一个上可能是 `EL_Happy_l_CLO` + `EL_Up`。这层映射住在 manifest 里,不写在代码里。

### 3.3 `expression-manifest.json` 结构（已落地）

与 `rig-manifest.json` 同构 —— 生产方产出，运行期只读，零名字判定。
**2026-10-17 起，下面是 `pipeline/expression-glb.mjs` 真实产出的形状**（不是草图）：

```jsonc
{
  "exprVersion": 1,
  "generatedAt": "2026-10-17T...",
  "slots": {                                  // 槽位表（UI 与校验共用，随规则表走）
    "happy":  { "cn": "开心", "group": "emotion" },
    "mouth_a": { "cn": "张嘴 あ", "group": "mouth" }
  },
  "groups": ["emotion", "blink", "eye", "mouth", "look", "brow", "symbol"],
  "models": [{
    "id": "si",
    "file": "si.charter.glb",
    "gazeMode": "none",                       // 'morph' | 'bone' | 'none'
    "blinkSource": "morph",
    "targetCount": 20,
    "targets": [                              // target 顺序 = morphTargetInfluences 下标
      { "index": 0, "name": "笑い", "verts": 63503, "affected": 3386, "sparse": true }
    ],
    "bindings": {
      "happy": [{ "ch": "morph", "target": 0, "name": "笑い", "w": 1 }],
      "shy":   [{ "ch": "material", "material": "表情", "materialIndex": 11,
                  "prop": "opacity", "mode": "add", "value": 1, "w": 1 }]
    },
    "overrides": { "happy": { "blink": "blend", "mouth": "blend" } },
    "unresolved": ["look_u", "symbol_sweat"], // 该模型没有实现 —— 必须报出来，不静默
    "coverage": { "covered": 22, "total": 35 },
    "sideChecks": [{ "slot": "blink_l", "morph": "ウィンク", "want": "left", "got": "left", "cx": 0.543 }],
    "warnings": []
  }]
}
```

**两处与初稿不同的实现决定（都是被数据推着改的）：**

1. **binding 用 `target: <索引>` 而不是 `mesh + target`。** 因为 `si` 的 14 个 primitive
   全部共享同一个 POSITION accessor、target 顺序也完全一致，所以「第几个 target」是全局
   唯一的。运行期按索引写 14 份 `morphTargetInfluences`（per-mesh 数组必须全写），
   不需要按 mesh 分组。`name` 保留只为人读日志。
2. **`shy` 是 material binding 而不是 morph binding。** `si` 的「照れ」是 PMX material
   morph（材质 11「表情」，`diffuse.a` 0→1 让表情图集渐显）。glTF 的 morph target 表达
   不了材质变化，所以 manifest 里记的是「改哪个材质的哪个属性、增量多少」，运行期施加。

`unresolved` 字段是纪律:**槽位表是跨模型统一的，但每个模型能实现哪些是事实。** 缺失就列出来，让消费方知道「这个角色做不了脸红」。这与 `rig-manifest.json` 里的 `unresolvedSlots` 是同一个设计。

### 3.3.1 左右归属：几何判定，不靠目视

MMD 骨架有强制的 `左目` / `右目`，而 wink 类 morph 只影响单侧眼周 —— 所以「ウィンク
到底是哪只眼」是**可以算出来的**：

```
sideOf(morph) = sign( morph 影响顶点的质心 X − 两眼骨骼中点 X )
```

`si` 实测：`ウィンク` 质心 `+0.543`、`ウィンク右` `−0.542`，`左目` 骨骼 `+0.291`
→ `ウィンク → blink_l`、`ウィンク右 → blink_r`。判定结果写进 manifest 的 `sideChecks`，
并由 `expression-glb.mjs` 在档案写错时报 warning。

**这条推翻了初稿里「必须拉权重渲一帧目视」的说法。** 当初这么写是因为只看了顶点数
（1,694 / 1,692 几乎同量）。顶点数确实说明不了问题，**质心的符号能**。

### 3.3.2 情绪的真实分量（实测，容易误判）

`si` 的 6 个情绪里，只有三个是「整脸」的，另三个只动眉毛：

| 槽位 | morph | 影响顶点 | 观感 |
| --- | --- | --- | --- |
| `happy` | 笑い | 3,386 | 眼睛笑弯 + 嘴角上扬（整眼区） |
| `relaxed` | なごみ | 3,386 | 同样整眼区，眼形更松 |
| `surprised` | びっくり | 3,320 | 睁眼 + 张嘴前态 |
| `angry` | 怒り | **180** | **只有眉毛**（降眉 + 眉间压紧） |
| `sad` | 困る | **180** | **只有眉毛**（八字眉） |
| `brow_angry` | 真面目 | **180** | 也是眉毛，与 怒り 观感接近 |

**推论：消费方要「生气」时只给 `angry` 是不够的** —— 还需要配合 `mouth` 或姿态叠加
（`PosePlayer` 的 additives），否则屏幕上只是眉毛动了 2px。这是资产事实，不是引擎缺陷；
manifest 的 `targets[].affected` 就是给消费方做这个判断用的。

### 3.4 通道所有权:单一写者原则的显式化

这是**本设计最关键的一个机制**,也是它和现有代码接得最顺的地方。

`src/anim.ts` 的文件头已经写死了一条原则:

> 与 PosePlayer 的关系:**互斥**。动画期间 mixer 是唯一写骨者,姿势层冻结。

这条原则要推广成一张全局的表:

| 属性 | 现有写者 | 表情层 |
| --- | --- | --- |
| `bone.quaternion`(身体槽位骨) | PosePlayer / AnimationMixer | **不碰** |
| `bone.quaternion`(`eye_l` / `eye_r`) | 无人 | **独占**(仅当 `gazeMode: 'bone'`) |
| `mesh.morphTargetInfluences[]` | 无人 | **独占** |
| 材质属性(diffuse / opacity) | 无人 | **独占**(material morph) |

**【判断】这里有一个非常有价值的结构性事实:表情层与姿势层/动画层天然正交。**

姿势层和动画层之所以必须互斥,是因为它们写**同一个属性**(`bone.quaternion`)。而表情层写的是 `mesh.morphTargetInfluences` —— **另一个属性**。所以:

> **表情可以和一个正在播的骨骼动画同时运行,不需要任何互斥协议。**

这意味着「挥着手同时笑」这件事零成本。**只有视线**是个例外:如果模型用眼骨做 LookAt(`rig.ts` 里 `eye_l/eye_r` 槽位存在),那视线就在写骨骼通道,需要遵守同一套单一写者规则。

**所以契约里必须有 `gazeMode` 字段**,声明这个模型走哪条路。`akane` 有 `look_*` 8 方向 morph(`gazeMode: 'morph'`,纯正交);没有视线 morph 的模型走 `bone`(需独占眼骨)。VRM 规范也是这么分的(Bone 模式 vs Expression 模式)【外部】。

**【判断】开发期应当有断言。** 在 dev 构建下,ExpressionLayer 与 PosePlayer 各自记录自己写过的对象 id,重叠即 `console.error`。这类 bug 的症状是「偶发穿模」,靠眼睛看很难定位。

## 4. 资产管线改造

### 4.1 三个新脚本

| 脚本 | 角色 | 产物 |
| --- | --- | --- |
| `pipeline/morph-survey.mjs` | **只读诊断**(已落地) | 终端报告:morph 类型分布、影响元素数、空壳检测、槽位覆盖率 |
| `pipeline/expression-rules.mjs` | **约定**(改规则改这里) | 被下面两个读取:槽位表、名字规则、模型档案 |
| `pipeline/expression-glb.mjs` | 转换器 | 读 PMX 的 morphs + 契约 GLB,把 morph target 写进 GLB,产出 `expression-manifest.json` |

沿用 `charter-glb.mjs` 的成熟模式:**规则与执行分离,原版永不改写,契约版单独产出。**

### 4.2 pmx2glb 的 morph 导出:一条比想象中短的路

**【实测】一个对实现极有利的结构事实:** 当前 GLB 里,15 个 primitive **共享同一个 POSITION bufferView**(`si` 的 14 个 primitive 全部指向 `bufferView 8`,`count = 63,503`)。这意味着顶点池是全局共享的。

这条事实让 morph 导出变得简单:

1. PMX 的 vertex morph 用**全模型顶点索引**描述位移(gli `elements[].index`)。
2. glTF 的 morph target 是 per-primitive 的 POSITION delta 数组,要求**顶点数与 base 一致**。
3. 因为 primitive 共享顶点池 → **一份全模型 delta accessor 可以被所有 primitive 的 `targets` 共同引用**。
4. 于是:每个 vertex morph 生成一个 delta accessor(all-vertex),15 个 primitive 各写 `targets: [{POSITION: 同一个accessor}]`。

数学上成立,不用做索引重映射。

### 4.3 体积预算:必须筛选,不能全导

**【实测】单个 morph 的 delta 成本 = 顶点数 × 12 字节**(3 × float32),因为 glTF 要求 delta 数组写满全部顶点(即使只影响 180 个顶点,其余位置也必须写 0)。

| 模型 | 顶点 | 单 morph(仅 POSITION delta) | 15 槽位增量 | 当前 charter GLB | 加后 |
| --- | --- | --- | --- | --- | --- |
| `yelan` | 34,799 | ~0.40 MB | ~6.0 MB | 9.7 MB | ~15.7 MB |
| `si` | 63,503 | ~0.73 MB | ~10.9 MB | 15.3 MB | ~26.2 MB |
| `akane` | 82,080 | ~0.94 MB | ~14.1 MB | 24.6 MB | ~38.7 MB |

`akane` 有 162 个 morph。全导 = 162 × 0.94 MB ≈ **152 MB**,不可接受。**必须按槽位表筛选。**

**【判断】三条压缩路径,按性价比排:**

1. **只导 POSITION delta,不导 NORMAL delta。** 体积直接省一半。理由:本项目面部走 **SDF 阈值场**驱动明暗(`src/npr.ts` 的 `NPR_IS_FACE` 分支),不依赖真实法线;卡通渲染下人脸本来就弱法线。
2. **筛选槽位**(必做)。第一版选 15 个左右核心槽位 → 增量 14 MB 上下,可接受。
3. **稀疏 accessor 或量化**。PMX 实测单个 morph 影响 180–3,386 个顶点。用 glTF `sparse` 能把**文件体积**压一到两个数量级(但 three.js 加载后会解压成全量数组,**显存占用不变**)。

### 4.3.1 实测：sparse 不是「可选」，是**默认**

第一版就上了 sparse，理由是它比预估的更划算，而且工具链完全支持：

- **glTF-Transform v4 有 `Accessor.setSparse(true)`**（标 `@experimental`，但 writer 的
  `concatSparseAccessors` 实现完整：base 全 0，只写非零元素）。因为 morph delta 天然
  以 0 为基值，这个「实验性」用法恰好是它最正确的用法。
- **three.js 的 GLTFLoader 完整支持 sparse**（`loadAccessor` 里 `bufferView === null`
  时先分配零数组再回填 sparse 值）。实测读取正常、`morphTargetInfluences` 索引对得上。

`si` 的实测账（20 个靶槽位、63,503 顶点池）：

| | dense | sparse | 省掉 |
| --- | --- | --- | --- |
| 20 个 morph 的 POSITION delta | 14.53 MB | **0.43 MB** | **97.1%** |
| 契约 GLB 总体积 | — | 15.01 MB | 与加 morph 之前持平（15.28 → 15.01） |

单 morph 的稀疏度只有 0.1%–5.3%（`ハイライト消` 44 个顶点 / `笑い` 3,386 个），
所以 sparse 在这里不是「压缩技巧」，是**数据结构与语义的自然匹配**。

**【判断】这条把「akane 全导 152 MB 不可接受」的结论改写了一半。** 152 MB 是 dense 的数；
sparse 下 162 个 morph 约 3.5 MB —— Phase 4 直接全导 `akane` 在体积上已经不成问题，
真正的成本变成**每帧写 82,080 × 162 个 influence 的带宽**（实测再说，先不下结论）。

### 4.4 material morph 必须单独处理

**【实测】`si` 的「照れ」(脸红)是 material morph**,`type = 8`,`elements = [{ index: 11, type: 1, diffuse: [0,0,0,1], ... }]`(材质索引 11,加法模式)。

glTF 的 morph target **只能作用于 POSITION / NORMAL / TANGENT**,表达不了材质变化。三条路:

- **A. 运行期施加**(推荐):manifest 里声明 `{ ch: 'material', index: 11, prop: 'diffuse', mode: 'add' }`,ExpressionLayer 直接改 `THREE.Material` 的对应属性。零资产改动,可控。
- **B. 转成顶点变形**:把「脸红」烘成腮红区域的顶点微位移 + 贴图替换。跨模型不通用。
- **C. 用 `KHR_animation_pointer`**:glTF 新扩展,能动画化任意属性。生态支持还不齐,`KHR_materials_variants` 是另一个思路。**不建议现在走。**

**【判断】选 A，已落地。** manifest 里是
`{ ch:'material', material:'表情', prop:'opacity', mode:'add', value:1 }`，
`ExpressionLayer` 每帧按 `charter.srcName` 重找材质再写 `opacity`（不持有引用——编辑器切
「契约轨道」会克隆材质实例，持引用会静默失效）。同材质多槽位取 **max** 而非相加
（`si` 的 `shy` 与 `symbol_blush` 共用这一层，叠加会过曝）。

关于 `morphOnly`：**它没有退场，但换了驱动源。** 原来是「有 morph 就显示」的门控
（`charter.ts` 的 `hasMorphs`），现在是**由口型权重驱动显隐**：嘴闭合（`mouth_*` 权重
≤ 0.02）时隐藏口内/舌/齿，张嘴才露出来。这条必须由表情层接管 —— 否则 si 一加载，
牙齿和舌头就永远悬在闭着的嘴唇前（`screenshots/expr-mouth-a.png` 是张开态对照）。

## 5. 运行期:`ExpressionLayer`

### 5.1 它在角色层的位置

```
src/
├── character.ts   加载契约资产          （已有）
├── rig.ts         骨骼槽位 + 姿势读写    （已有）PosePlayer 写 bone.quaternion
├── anim.ts        外部动画播放           （已有）AnimationMixer 写 bone.quaternion
└── expression.ts  表情层                （新增）写 morphTargetInfluences + 材质 + 眼骨
```

三者的关系一句话:**`rig` 管骨头的怎么摆,`anim` 管动作怎么放,`expression` 管脸怎么变。前两者互斥,第三者与它们正交。**

### 5.2 核心 API（**已实现**，`src/expression.ts`）

```ts
export class ExpressionLayer {
  constructor(root: THREE.Object3D, model: ModelExpression,
              slots, groups);

  /** 语义槽位 → 权重。0 = 关闭，1 = 满。持有到下次设置（不自动回落） */
  set(slot: string, weight: number, fade?: number): void;

  /** 播一次再回落（一次性演出） */
  play(slot: string, opts?: { hold?: number; fade?: number; release?: number; w?: number }): void;

  /** 全清（含待回落的） */
  clear(): void;

  /** 自动眨眼开关（默认开） */
  setAutoBlink(on: boolean): void;

  /** 该模型能否做这个槽位 —— 消费方先问再做，而不是默默没反应 */
  has(slot: string): boolean;

  /** 每帧推进：释放 / 眨眼 / 插值 / 写 influences / 写材质 / 口内件显隐 */
  update(dt: number): void;

  /** 当前真实生效的权重表（测试断言与调试面板用） */
  readonly effective: Readonly<Record<string, number>>;
  readonly slots: Readonly<Record<string, { cn: string; group: string }>>;
  readonly groups: readonly string[];
}
```

**实现里三个值得记的点：**

1. **`update(dt)` 必须与骨架动画同时基。** `stage.ts` 把它拍在与 `pack.update` 同一个
   30fps 节流块里 —— 否则慢帧时脸会比身体先动。编辑器里用真实 dt（淡化更顺），上限 0.1s。
2. **权重是 per-mesh 的，14 个 primitive 各有一份 `morphTargetInfluences`。** 实测 14
   份数组长度都是 20、写入后逐位相同（验证脚本断言 `distinct === 1`）。manifest 只存
   一个 target 索引，写入时扇出到全部网格。
3. **`update(0)` 有意义（且必要）。** 编辑器加载后先跑一帧 dt=0，口内件在「嘴闭」状态
   被隐藏，随后抓的可见性基线才是对的 —— 否则「隔离材质」模式会把牙齿重新打开。

**未实现（Phase 3）：** `gazeAt` / 视觉游移。`si` 的 `gazeMode` 是 `none`（没有 `look_*`
morph），`akane` 才是 `morph`。不做「假装有」的 API。

### 5.3 仲裁:override(none / block / blend)

**【外部】抄 VRM 1.0 的语义。** 当一个情绪槽位和一个底层槽位同时激活,按 `overrides` 表决定:

| 策略 | 行为 | 用在哪 |
| --- | --- | --- |
| `none` | 不干预,两者叠加 | 默认 |
| `block` | 情绪激活时,把底层强制归零 | 硬切(如「闭眼笑」时禁用自动眨眼 —— 但 `akane` 用 `_CLO` 变体更好) |
| `blend` | 底层权重随情绪权重线性衰减 | **推荐**。`happy = 0.8` 时,眨眼权重被压到 0.2 倍,眼皮不会穿过笑容 |

VRM 规范的推荐默认值:`happy` / `angry` / `sad` 三者的 `overrideBlink` 与 `overrideMouth` 都设 `blend`【外部】。

**【判断】`akane` 这类带 `_CLO` 变体的模型走第四条路:**不靠 override,靠**切换变体**。情绪权重高且正在眨眼时,整体切到 `EL_<情绪>_CLO`,权重交叉淡化。这比 override 干净(不用两组顶点位移互相打),代价是要求资产自带变体。契约里用 `variants: { happy: { open: 12, closed: 45 } }` 声明。

### 5.4 自动层:让角色「活着」而不用下指令

三个程序化行为,**它们在没有任何外部指令时也应该跑**:

| 行为 | 做法 | 参考 |
| --- | --- | --- |
| **自动眨眼** | 随机间隔(建议 2–6 s,对数正态分布),闭眼 60–90 ms,Hold 40 ms。任何情绪激活时按 override 降权 | ChatVRM 的 `AutoBlink`、Agent-desktop-pet 的惯性回正 |
| **视线游移** | 无目标时做低频随机注视点(周期 3–8 s),有目标时向目标 lerp | waifu-rt3d 的 `L5 LookAt (always additive)` |
| **情绪衰减** | 情绪权重按指数曲线回落(半衰期建议 2–4 s),可被「保持」指令冻结 | Open-LLM-VTuber 的「表情持续到下一个标签或对话结束」 |

**【判断】衰减曲线是本项目必须补的一环。** 参考项目大多数是「保持到下一个标签」,对陪伴型桌宠够用;但放置游戏里角色长时间无人交互,一个僵在 `angry` 的脸上很难看。**必须有自然回落。**

### 5.5 与 PosePlayer 叠加层的关系

`rig.ts` 的 `PosePlayer` 已经有一套成熟的叠加层机制(`additives`:呼吸 `breath`、重心轻摆 `sway`、手臂微垂 `idle_arm`),用永不停止的 `clock` 驱动相位。

**【判断】情绪的姿态部分不要自己写骨,复用它。** 具体做法:ExpressionLayer 持有一个 `additiveGain` 与一组情绪姿态预设,通过 `PosePlayer` 的 `opts.additives` / `additiveGain` 注入。

这样做的价值:**情绪层永远不写 `bone.quaternion`,单一写者原则自动成立。** 「开心」= 表情权重 + 姿态叠加增益,两条腿都走既有通道。

## 6. 指令协议:`witch.exp/1`

最小可用的设计目标是:**让外部系统的每一条意图,都能翻译成一条无歧义的数据。**

### 6.1 指令集（已冻结）

权威定义在 **`docs/表情层-对外契约.md`** 与 `src/exp-contract.ts`；这里只留与设计初稿的出入。

```ts
type ExpCommand =
  // —— 表情 ——
  | { op: 'face.set';   slot: string; w?: number; fade?: number }
  | { op: 'face.play';  slot: string; w?: number; hold?: number; fade?: number; release?: number }
  | { op: 'face.clear'; slots?: string[] }
  | { op: 'face.auto';  what: 'blink' | 'gaze'; on: boolean }

  // —— 口型 ——
  | { op: 'mouth.set';   viseme: string; w?: number }
  | { op: 'mouth.clear' }

  // —— 视线 ——
  | { op: 'gaze.dir';  x: number; y: number; fade?: number }   // 归一化方向
  | { op: 'gaze.at';   target: [number, number, number] | null }

  // —— 动作（转交动作系统） ——
  | { op: 'motion.play'; id: string; loop?: boolean; fade?: number }
  | { op: 'motion.stop' }

  // —— 语义打包 / 复位 ——
  | { op: 'emote'; slot: string; motion?: string; hold?: number; release?: number; w?: number }
  | { op: 'reset' };
```

**与初稿的三处出入，都是落地时改的：**

1. **删掉 `seq` / `par`。** 表情是事件驱动、动作是采样驱动，两套时间线混进一个指令必然要处理取消语义，而收益只是省一次调用。`emote` 已经覆盖最高频的组合；更复杂的编排属于动作系统或游戏侧状态机。
2. **`face.auto` 的 `what` 从 `'blink'|'gaze'|'decay'` 收敛为 `'blink'|'gaze'`。** decay（情绪衰减）是内部机制，不是消费方该开的东西。
3. **新增 `gaze.dir`。** 连续视线要的是「看向哪」，不是「8 个离散方向里的哪个」；`gaze.at` 是它的世界坐标版本。两者最终都落到同一套 `look_*` 权重或眼骨角度。

### 6.2 `emote` 是给消费方用的糖

消费方最常写的场景是「她开心地挥手」。用原子指令要写三条(`face.play` + `motion.play` + 定时 `face.clear`)。所以给一个语义打包:

```ts
{ op: 'emote', slot: 'happy', motion: 'wave', hold: 2.0, autoRelease: true }
```

**【判断】这一条是「指令控制」这个需求的核心。** 消费方的 LLM 桥只要输出 `{ emote: 'happy', motion: 'wave' }`,剩下的时序(动作等待、表情持续、衰减回落)全由引擎的自动层兜住。

### 6.3 优先级与冲突

```
高  ┌ 显式指令 face.set / emote           （外部调用）
    │ 保持类指令 face.play { hold }         （定时释放）
    │ 自动层 blink / gaze / decay           （无指令时兜底）
低  └ 空闲默认态
```

规则三条:

1. **同槽位后来者覆盖前者**,并按 `fade` 交叉淡化。同一帧内多条同槽位指令,取最后一条。
2. **自动层让位于任何显式指令同槽位**。外部 `face.set('blink', 1)` 时,自动眨眼暂停,直到 `face.auto('blink', true)` 或该指令释放。
3. **`motion` 与姿势层严格互斥**(既有规则):`motion.play` 期间,消费方自行决定姿势层怎么处理 —— 沿用 `CharacterAnim.onStop` 回调把姿势接回来。

### 6.4 与 `witch.clip/1`(`PoseClip`)的关系

两者是**并行的两套时间线**,不是一个系统的两种形态:

| | `witch.clip/1`(姿势) | `witch.exp/1`(表情) |
| --- | --- | --- |
| 写什么 | `bone.quaternion` | `morphTargetInfluences` + 材质 |
| 驱动单位 | 关键帧(`keys[].t` + `pose`) | 指令(事件式,不是采样式) |
| 时间语义 | 连续采样 | 置位 + 自动衰减 |
| 与动画的关系 | **互斥** | **正交** |

**【判断】表情不做成「关键帧 clip」而做成「指令流」的理由:** 姿态是要逐帧采样的连续量(平滑插值很关键),表情是**事件驱动**的离散状态变化(「现在开始开心」),而且天然带衰减。硬做成关键帧反而会让消费方每帧算权重。**但两者最终都写进同一个 `update(dt)`**,由 `stage.ts` 的帧循环统一调度。

### 6.5 缺能力时的回退与提示

**【判断】这是契约里最容易被写错、也最容易被低估的一条。**

「调用模型不存在的能力」在三只模型之间是**常态**，不是异常：`si` 只有 22/35 槽位、`yelan` 连表情层都没有。如果引擎这时什么都不做，上游永远发现不了自己的 bug——屏幕上没反应，日志里也没有。

所以约定写死三级回退，并且**每一级都必须发一条 `ExpNotice`**：

| 情形 | 回退到 | notice |
| --- | --- | --- |
| 槽位不可用，但同义槽位可用 | 同义槽位（只登记「共用同一份资产」的对，如 `symbol_blush ↔ shy`） | `slot-alias` |
| 槽位不可用，无同义 | 该组**清到中性**（不是保持上一次） | `slot-neutral` |
| 整个模型没有表情层 | 丢弃表情部分，动作照转交 | `no-expression` |
| `motion` 不存在 | 动作系统 `idle` | `motion-unavailable` |
| op 不认识（跨版本） | 丢弃该条 | `unknown-op` |

「组级清到中性」而不是「保持」的理由：保持会让「她说她生气了」之后一直挂着怒眉，直到下一条指令。**默认态应该是中性，不是上一次的状态。**

消费方拿结果的两种方式：`apply()` 的返回值 `{ ok, applied, notices }`，或 `setNoticeSink(cb)`。`ok === false` 的语义是「降级了」，不是「出错了」——这条区分对上游很重要。

唯一实现是 `src/exp-contract.ts` 的 `resolveSlot()`（纯函数，可单测）。`ExpressionLayer` 自己**不做**回退判断，它只负责「能不能写」；回退是协议层的职责。

`waifu-rt3d` 的 L0–L5【外部】映射到本项目,能看出**我们不是从零开始**:

| 层 | 职责 | 本项目现状 | 本设计要做的 |
| --- | --- | --- | --- |
| **L0 基础姿态** | 呼吸、重心、手臂微垂 | ✅ **已有** —— `PosePlayer` 的 `additives`(`breath` / `sway` / `idle_arm`) | 不动 |
| **L1 待机行为** | 随机小动作 | ⚠️ 有骨架无内容 | 后续:复用 `anims/*.anim.glb` 机制 |

**【判断】明确不做:**

- **不做面部捕捉(ARKit / 摄像头)。** 那是另一个量级的产品形态,与 diorama 放置游戏无关。

| 风险 | 说明 | 对策 |

### 10.4 Phase 3（指令面 + 视线 + `akane` 启用）

**实数（`akane`）**

```
[pmx] 顶点=82080 面=115661 材质=15 骨骼=620 贴图=8 morph=162
[expr] model=akane  gaze=morph(±18°)  blink=morph
  目标 35 个（槽位引用 35）· 覆盖 35/35 槽位
  delta 体积 dense 32.88 MB → sparse 0.67 MB（98.0% 省掉）
[glb] akane.glb 53.40 MB → akane.charter.glb 24.27 MB
```

**三个决策与理由**

1. **契约冻结点放在 `exp-contract.ts`，不是 manifest。** manifest 是转换期产物，结构会随资产演进（这轮就从 v1 加了 `capabilities` / `gaze` / `fallback`）；对外承诺必须是一个手写的、能升版本的 TypeScript 文件。消费方 import 它，不 import JSON。
2. **回退语义做成纯函数 `resolveSlot()`。** 因为它要被三处调用（协议层、编辑器能力显示、将来的单测），而且是最容易写歪的一段逻辑 —— 放在有类型、无副作用的地方，改一次就有编译期保护。
3. **视线两套实现，一个指令。** `akane` 有 8 方向 `look_*`（相邻两方向线性插值，`gazeWeights()`）；`si` 只有眼骨（`左目`/`右目`，rest 之上局部后乘）。消费方只写 `gaze.dir`，不关心底下是 morph 还是骨。

**两个只有拍图才发现的坑**（写进代码注释，别再踩）：

- **「眼骨」不等于「眼球骨」。** `si` 的层级是 `左目`(眼球) → `瞳左`(瞳孔贴片，挂在眼球前方)。`rig-rules` 把 `eye_l` 槽位映射到 `瞳左`，但转瞳孔贴片只是让它自转 —— ±10° 和 ±20° 两版截图里瞳孔**都没平移**。视线必须显式指定 `左目/右目`。
- **`look_L`/`look_R` 可能是观众视角命名的。** `akane` 实测：`gaze.dir(1,0)`（看角色右）点亮 `look_R` 后瞳孔偏向**观众右侧**（= 角色左侧）。契约方向是角色视角，所以档案里声明 `mirrorX: true`，运行期横向取反。这件事不能靠猜，只能看瞳孔往哪边移。

**实测（无头 Chrome，`?noviewer=1`，页面内调 `__editor.exp()`）**

| 检查项 | 结果 |
| --- | --- |
| `akane` 能力 | 35/35 槽位 · 35 targets · `gaze=morph ±18°` · 眨眼 · 无材质通道 |
