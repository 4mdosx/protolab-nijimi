# 现状评估：nijimi 作为「人物动作细腻 / 画面 / 特效丰富」的放置游戏展示层

> 评估时间 2026-10-19。数据来自当前 `main`（ef8c8f4）实测，不是估算。
> 衡量的对象是**展示层**，不是「引擎是否优雅」——所以「代码写得干净但游戏侧用不上」也算缺陷。

---

## 0. 结论先说

**画一张画的能力已经到了能拿出去给人看的水准；演一场戏的能力还是零件状态。**

三句话概括：

1. **材质、着色扩展、后期链、表情层**是成熟的，内容侧不改引擎就能加效果——这部分不用再投入。
2. 缺的不是着色器，是**表演运行时**：谁在什么时刻写骨骼、写表情、动镜头、放特效。现在这四件事没有仲裁者，`PosePlayer` 和 `CharacterAnim` 甚至是互斥的两套零件，舞台一行业务都没接。
3. 交付工程（体积 / 加载 / 多角色 / 性能分级）基本是空白。单角色 9.3 MB、单帧 816 次 draw call、动画固定 30 fps、阴影 2048 固定——本地开发完全够用，装进 WebView 就是另一回事。

评分（10 分制，仅代表「现在能不能直接做展示层」）：

| 维度 | 分 | 一句话理由 |
| --- | --- | --- |
| 单帧画面 | 8.0 | NPR + 彩色 IBL + Bloom + 调色，风格统一，能出样张 |
| 特效表现力 | 6.5 | 模块与 pass 的扩展性很好，但**成品特效件太少**，只有粒子/冲击波/描边 |
| 人物动作细腻度 | 4.0 | 骨架、语义欧拉、姿势库都在，但没有分层混合、没有 IK、舞台没接线 |
| 交付工程 | 3.5 | 无压缩、无进度、无缓存、无质量分级、无释放路径 |
| 内容扩展性 | 8.5 | 层 A/B/C 三层扩展 + `ScenePack` 契约，游戏侧确实不用改引擎 |

**判定：现在适合做「一张会动的画」（登录页、角色展示、单段演出）；不适合做「一场连续几个月的表演」（放置游戏主界面）。** 补完第 4 节的 M1 + M3 之后可以。

## 2. 实测数字

环境：Chrome headless，ANGLE Metal，视口 1440×900，`deviceScaleFactor: 2`
→ 实际画布 **2880×1800**（3.1 MP）。采 30–60 帧取中位数。这是一台带独显的 Mac，**不代表手机**。

### 2.1 一帧的成本（集成编辑器，角色 + 完整工坊）

| 指标 | 数值 |
| --- | --- |
| draw calls / 帧 | **816** |
| 三角形 / 帧 | 401 484 |
| 帧时间中位数 | 35.2 ms（≈28 fps） |
| 关 Bloom | 803 calls / 29.9 ms（Bloom ≈ 5 ms） |
| 关阴影 | **381 calls / 103 091 tris**（-53% calls，-74% tris） |
| 场景构成 | 191 mesh / 111 材质；角色 16 mesh / 16 材质（全 skinned） |
| 着色程序 | 51 个 |
| 纹理 / 几何 | 48 / 191 |
| 后期链 | `scene → bloom → grade → tonemap → encode`，MSAA×4，HalfFloat |

两个结论：

- **阴影 pass 是最大单项开销**：关掉它立刻少 435 次调用和 298k 三角形。原因是阴影相机范围（±7）比正交视锥大得多，把画面外的陈设也画了一遍；角色 6 万面在阴影里又画一次。
- **111 个房间材质换来 191 个 mesh**：每个 mesh 一次调用，没有合并、没有 instancing。放置游戏再往里加 3 个角色 + 20 个特效件，会稳定突破 1500 calls——那是移动端的死线。

### 2.2 角色资产体积

| 资产 | GLB | 其中 PNG 贴图 | 顶点 | 材质 |
| --- | --- | --- | --- | --- |
| `yelan.charter.glb` | 9.3 MB | 6.9 MB（5 张） | 34 799 | 16 |
| `si.charter.glb` | 15.0 MB | 10.2 MB（8 张） | 63 503 | 14 |
| `akane.charter.glb` | 24.3 MB | 17.7 MB（8 张） | 82 080 | 15 |

**贴图占了 75%。** 全部是未压缩 PNG，没有 KTX2/Basis，没有 Draco，没有 mip 之外的纹理复用。一个 9 MB 的角色在 4G 上首屏 3–6 秒，在弱网 WebView 里更久——而引擎**没有加载进度、没有取消、没有缓存**（`THREE.Cache` 都没开）。

### 2.3 动画语料

`assets/models/anims/` 里只有 `demo-wave.anim.glb` 一个文件。骨骼槽位、语义欧拉、姿势→clip 的转换都在，但**没有动作库**。这是内容缺口，不是代码缺口，但它决定了「动作细腻」这件事今天无从谈起。

## 3. 缺陷清单

按「会不会直接挡住展示层这个定位」排序。每条给出证据，不写「可能」「建议关注」这类废话。

### P0：挡住定位

**① 舞台没有表演运行时，动画零件没接线**

`stage.render()` 里只有两句和角色表演有关的：

```ts
packInst.update?.(animStep, clock.context.animTime);
character?.expression?.update(animStep);
```

`PosePlayer` / `CharacterAnim` 在 `src/` 内**零引用**，只在 `editors/pose.ts` 里用。也就是说：游戏侧拿到 `stage.character()` 之后，骨骼是 T-pose/rest，表情会眨眼，身体不会呼吸。

后果：任何「角色在工位上干活」的画面都要游戏侧自己 `buildRig` + `new PosePlayer` + 每帧 `update`；而 `src/anim.ts` 头注释明确写着「与 PosePlayer **互斥**，两者同时写骨会打架」——却没有仲裁者。

**② 单角色硬编码，且长驻舞台上换角色会泄漏显存**

`createStage({ characterId })` 只接受一个 id，舞台内没有「加/删角色」的路径。`loadCharacter()` 每次调用都重新下载（`THREE.Cache` 未启用），而 `stage.dispose()` 只调 `characterRendering.dispose()`——**那只释放 SDF 贴图**。

真正释放几何与材质的 `discardPreparedCharacter()` 已经写了，但只有编辑器在「异步切换被新请求取代」时调用；舞台自己不调。于是长驻舞台换角色 / 换装 = 旧网格与材质的 GPU 资源永远留着。放置游戏恰恰是「角色常驻 + 频繁换装」。

**③ 资源交付没有一条流水线**

无 Draco、无 KTX2、无 LoadingManager、无进度回调、无超时/重试、无 per-character bundle。上面 9–24 MB 的体积是直接怼给浏览器的。

**④ 性能没有分级，也没有降级路径**

- 阴影图 2048×2048 固定（`stage.ts`）
- `setPixelRatio(Math.min(devicePixelRatio, 2))` 固定
- MSAA×4 + HalfFloat 固定
- `ANIM_FPS = 30` 是常量，不可配
- 软粒子深度预 pass 只要开了就每帧跑，哪怕当前没有任何运动粒子（文档 §7-7 已自认）

移动端没有任何一档可以退。展示层要跑在手机上，这条是硬伤。

**⑤ 镜头只有「看哪儿」，没有「怎么拍」**

`stage.view` 只有 `zoomBy` / `panByPx` / `reset`，且 `view.zoom` 的 setter 是空实现：

```ts
set zoom(_: number) { void _; }   // 写进去静默无效
```

这是个 API 陷阱（外部读 `stage.view.zoom` 拿得到值，写却什么都不发生）。更实际的问题是：**推近、拉远、摇镜、焦点切换、震屏**这些「细腻」的一半都靠镜头，现在一个都做不了。

### P1：限制表达上限

**⑥ 动画只有「一段 clip 独占」，没有混合**

`CharacterAnim.play()` 换 clip 就是交叉淡化整段；没有上半身/下半身遮罩、没有 additive 叠加（只有 `PosePlayer` 里的正弦呼吸）、没有 loop 区间、没有事件回调（脚步/转身触发音效或特效）、没有 root motion、没有 foot IK。
手持道具（法杖、扫帚、坩埚勺）也**没有骨骼挂点 API**——只能按角色局部坐标硬摆。

**⑦ 骨骼与表情没有时基仲裁**

表情走 30fps 累加器（`stage` 里），`CharacterAnim.mixer` 若被游戏接上会走真实 dt，姿势层又只认自己的 `clock`。三者都写同一副骨架的不同属性，短期能跑，长期一定会出现「慢帧时脸比手先动」或「暂停时呼吸还在」。

**⑧ 特效件太少，且没有统一 spawn 接口**

现有成品：`ElementParticles`（CPU `Points` + 径向贴图，五种元素各一个系统）、`createShockwavePass`、`createDepthEdgePass`。
缺：ribbon/trail、地面 decal、mesh beam（光柱/锁链）、GPU 粒子、attractor/burst 生命周期、软贴面。而且粒子是「一种元素一个固定系统」，没有「在某个世界坐标炸一下」的 API——放置游戏的反馈密度全靠这个。

**⑨ 后期缺「镜头感」的三件套**

无 DoF（角色编辑器里曾有 Bokeh，舞台没有）、无接触阴影/SSAO（`post` 只给 color + depth，法线缓冲没有）、无 LUT 分镜调色。颗粒/色差/景深这类「让画面不像实时渲染」的东西目前是零。

**⑩ 演出之间没有优先级**

`EffectSpec` 的纪律是「一个参数只有一个写入者」。常驻光环（loop 演出）+ 触发爆发（一次性演出）同时写 `uRimPulseStrength` 会被审计拒绝并记 `param-conflict`。需要一个混合/优先级策略（乘法叠加 / 取 max / 后写覆盖并显式声明），而不是让内容侧自己错开参数名。

**⑪ 时间线只有标量轨道**

颜色/向量只能当常量；没有事件轨道（到 0.42 相位触发一次「镜头推近 + 音效 + 表情切换」）。这让「演出」只能调数值，不能编导。

### P2：工程与可维护性

| # | 问题 | 证据 |
| --- | --- | --- |
| ⑫ | 交互验收脚本不在仓库里 | 六台编辑器的 playwright 脚本都在 `/tmp`，`package.json` 没有 test 脚本 |
| ⑬ | 库产物没有构建 | `exports` 直接指 `./src/index.ts`，只能靠 Vite 源码消费；无 `.d.ts` 打包 |
| ⑭ | 文档硬伤（本次已修） | `docs/职责边界.md` 代码块未闭合，把 §6 吞进代码块；「五台编辑器」已过时 |
| ⑮ | `render(dt, elapsed)` 的 `elapsed` 被忽略 | `function render(dt: number, _elapsed: number)`，签名误导 |

| ⑰ | 法线缓冲缺失 | `post.add` 遇到 `reads: ['normal']` 直接抛错，挡住 SSAO/法线类 pass |

## 4. 要补什么

按「能看 → 耐看 → 撑得住」三档排。**不要同时开三条线**，M1 不做完，M2 的精细动作没有地方播。

### M1「能看」——一场完整的展示

1. **表演运行时 `Performer`**（最重要，一条顶五条）
   ```ts
   const perf = createPerformer(character, { rig, clips, expression });
   perf.play('work_loop', { layer: 'base', fade: 0.35 });
   perf.play('breath',      { layer: 'additive', gain: 0.8 });
   perf.play('happy',       { layer: 'overlay', fade: 0.2 });
   perf.on('step', () => fx.spawn('dust', { at: 'foot_l' }));
   ```
   职责：**唯一写骨者**、三层混合（base / additive / overlay）、统一时基、事件轨道、clip 切换不打架。这是把 `PosePlayer` + `CharacterAnim` + `ExpressionLayer` 收进一个调度器，而不是再造一套。

2. **镜头 `ShotDirector`**
   正交相机也能拍：zoom 曲线 = 推拉，target 平移 = 摇镜，`view` 已有锚点缩放。加上 `shot(name, { dolly, pan, hold, ease, shake })` 和「按世界点构图」。**没有这个，角色再细腻也像商品展示图。**

3. **特效件补齐到 6 类**
   `spawn(kind, { at, dir, count, life })` 统一入口 + ribbon、decal、mesh beam、burst 粒子。放置游戏的「爽点」全靠打击/收获/升级三种反馈，每种至少两件。

4. **多角色 + 生灭周期**
   `SkeletonUtils.clone` + 每角色独立材质实例（或共享材质 + 参数覆盖），`stage.characters.add(id) / remove(id)` 带完整 dispose。放置游戏通常「常驻 1 主角 + 若干背景角色」。

5. **资源交付**
   Draco（几何）+ KTX2/Basis（贴图）+ `LoadingManager` 进度 + abort + 内存/IndexedDB 缓存。目标是**角色 < 2 MB**，首屏 < 1.5 s。

### M2「耐看」——细腻度

6. 动画遮罩与 additive 层（上半身说话 / 下半身干活）
7. 手部挂点 `attach(slot, object)`，法杖/工具不再手摆
8. foot IK 或至少「脚底贴地」校正（写实姿势在斜面上会飘）
9. 事件轨道贯通：骨骼事件 → 特效/音效/表情，全部同一条时间轴
10. 后期三件套：DoF、接触阴影、LUT 分镜
11. 次级运动：`rig.physChains` 已存在，但只在姿势层，接进动画层即可

### M3「撑得住」——交付

12. **画质档位** `quality: 'low' | 'mid' | 'high' | 'auto'`
    一档一个组合：DPR（1 / 1.5 / 2）、阴影（关 / 1024 / 2048）、MSAA（0 / 2 / 4）、Bloom 分辨率（1/4 / 1/2 / 1）、软粒子深度 pass（关/按需/常开）。
13. **性能预算与自动降级**：每帧采样 calls/tris/ms，连续超预算 2 s 降一档，并在 `notices` 里出声（沿用现有提示通道）。
14. **静态几何合并 + InstancedMesh**：房间 111 材质 → 目标 < 40；阴影 caster 白名单（只有角色和主要家具投影）。
15. **后台暂停**：`visibilitychange` → 停 rAF、停 mixer、保留相位。
16. **把验收脚本搬进仓**：`e2e/*.mjs` + `npm run check:e2e`，六入口冒烟 + 演出断言 + 预算快照。

## 5. 明确不建议做的

- **不要为「细腻」上运行时布料/全身 IK**。移动端 ROI 极低，DCC 烘焙 + 少量程序化（呼吸、视线、足底校正）足够骗过眼睛。
- **不要在引擎里开 2D 纸娃娃的第二条腿**。`witch-idle` 的「AI 帧按需生成」是另一条技术路线，混进来会让「同一张画」这个前提失效。
- **不要给引擎加游戏概念**（数值、背包、时间银行）。职责边界已经很清楚，别为了「方便」把 `witch-idle` 的模拟层吸进来。
- **不要先做 UBO / 材质变体优化**。当前 51 个 program 不是瓶颈，816 次 draw call 才是。

## 附：数据是怎么测的

- draw call / 三角形 / 帧时间：`renderer.info.autoReset = false` → `reset()` → 采 30–60 帧后取均值；帧时间取 rAF 间隔中位数。
- 阴影开销：`scene.traverse` 把 `castShadow` 全关 + `shadowMap.enabled = false` 后同法采样。
- GLB 体积构成：直接读 GLB 的 JSON chunk，累加 `images[].bufferView.byteLength`。
- 已知偏差：headless + ANGLE Metal，帧时间**只能横向对比**（同机同场景开关效果），不能当作真机绝对值；draw call 与三角形数是准确的。
